Hard Limits Discovered

<tt>swapon</tt> is impossible inside Docker containers

What happened: gem5_setup.sh tried to create a swap file inside the container to give the gem5 linker more virtual memory. Failed with:

swapon: /swapfile_gem5: Invalid argument

Tried both with and without --privileged. Same result.

Root cause: Docker uses the overlay2 filesystem. The Linux kernel does not allow swap files on overlay filesystems — kernel-level restriction, no workaround inside the container.

Fix applied: Removed the entire swap setup block from gem5_setup.sh. Job count is controlled solely by AVAIL_MB / 1500, capped at nproc.

What to do instead: If more swap is genuinely needed for a heavy build, add it on the host before starting the container. The container inherits host swap automatically.

Stale container memory cap — container sees less RAM than host

What happened: docker exec rvpoint-dev free -h showed 5.6 GB even though the host has 23 GB RAM.

Root cause: Old container was created with a stale --memory cap from somewhere. rvpoint.sh does NOT set --memory, so newly created containers are uncapped and see all host RAM.

Fix: docker stop rvpoint-dev && docker rm rvpoint-dev, then re-run rvpoint.sh to recreate. Verify with docker exec rvpoint-dev free -h — should show ~23 GB.

Detection: ‘docker inspect rvpoint-dev --format ’{{.HostConfig.Memory}}'` — non-zero means a hard cap is in place.

gem5 <tt>inst-constrs.cc</tt> compilation OOM-killed even with moderate parallelism

What happened: gem5 build killed cc1plus (the C++ compiler frontend) during compilation of arch/riscv/generated/inst-constrs.o even with a formula-capped job count.

Root cause: inst-constrs.cc is gem5's auto-generated RISC-V instruction constraint file — approximately 300K lines of C++. A single compilation of this file needs 4–6 GB of RAM at -O2. Running even 2–3 of these concurrently exhausts available memory.

Fix: Changed job count divisor from AVAIL_MB / 1500 to AVAIL_MB / 4000. On 23 GB RAM this yields 5 jobs — enough parallelism to be reasonably fast, conservative enough to survive large generated file compilations.

gem5 linker OOM-killed with high parallelism

What happened: gem5 build with -j$(nproc) (16 jobs) killed the linker with signal 9 [Killed] during the gem5py_m5 link step.

Root cause: gem5py_m5 and gem5.opt link steps each need ~3–4 GB of virtual memory. With 16 parallel jobs, multiple linkers run simultaneously and exhaust available RAM.

Fix: Cap -j using AVAIL_MB / 1500 (1 job per 1.5 GB), bounded by nproc. With 23 GB host RAM this yields ~15 jobs — safe because not all jobs are linkers simultaneously.

<tt>mkswap -q</tt> flag does not exist on Ubuntu 22.04

What happened: mkswap -q "$SWAPFILE" failed with:

mkswap: invalid option -- 'q'

Fix: Replace with mkswap "$SWAPFILE" > /dev/null.

gem5 v24 does not support all RVV instructions — <tt>normal_rvv</tt> hits <tt>IllegalInstFault</tt>

What happened: gem5 aborted with IllegalInstFault during normal_rvv simulation. Because set -e was active, the entire benchmark script died.

Root cause: gem5 v24.0.0.1 implements only a subset of RVV v1.0. normal_estimation_rvv uses advanced indexed/compressed vector ops (vluxei32, vcompress, etc.) that aren't fully implemented. gem5 aborts instead of raising a recoverable error.

Fix: In run_gem5(), append || true to the gem5 invocation. Detect IllegalInstFault in stdout and write a .failed marker. extract_cycles returns UNSUPPORTED when the marker exists. Speedup calculation skips UNSUPPORTED entries. Report shows UNSUPPORTED instead of crashing.

Affected algorithms: normal_rvv, pipeline_rvv, pipeline_sc (scalar pipeline calls extract_plane_outliers_rvv — no scalar version exists, hits vlseg LMUL panic). normal_sc, voxel, ransac, sor all work fine.

Also: gem5 v24 renamed sim_insts → simInsts in stats.txt. extract_insts now tries simInsts first with sim_insts as fallback.

gem5 v24 requires <tt>SEWorkload</tt> set on the system object

What happened: gem5 SE mode failed immediately with:

fatal: fatal condition !seWorkload occurred: Couldn't find appropriate workload object.

Root cause: gem5 v23+ changed the SE mode API. system.workload must be set to an SEWorkload object before the process is assigned. Older examples only set system.cpu.workload = process which no longer works.

Fix:

from m5.objects import SEWorkload
system.workload = SEWorkload.init_compatible(args.cmd) # ← add this before Process setup
process = Process()
process.cmd = cmd
system.cpu.workload = process
system.cpu.createThreads()

Docker Desktop for Linux uses a QEMU VM — limits container RAM to ~5.6 GB

What happened: Container consistently saw 5.6 GB despite host having 23 GB. docker info showed Total Memory: 5.612GiB. No --memory flag was set.

Root cause: Docker Desktop for Linux runs all containers inside a QEMU VM with a default 6 GB allocation. The host RAM is irrelevant — containers see the VM's RAM.

Fix: Remove Docker Desktop (sudo apt-get remove --purge docker-desktop), use Docker Engine (docker-ce) directly. Engine runs natively with access to all host RAM. Also remove leftover credential helper: {"credsStore": "desktop"} from ~/.docker/config.json.
