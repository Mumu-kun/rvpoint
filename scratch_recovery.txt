You have **two distinct architectural choices** depending on whether you want to keep the tree hierarchy or replace the structure entirely:

---

### Option 1: Replace *Just the Pointer Chasing* (Linear Array Octree)
You **keep the full Octree hierarchy and variable depth**, but eliminate heap node pointers (`node->children[i]`):
* **How it works**:
  * Instead of dynamic `new PointerOctreeNode()` objects scattered randomly across the heap, all nodes are stored in a **single flat contiguous array** (`std::vector<OctreeNode>`).
  * Child navigation uses array index arithmetic: $\text{child\_idx} = 8 \times \text{parent\_idx} + \text{child\_code}$.
* **Pros**: Preserves the variable-depth octree concept and logarithmic adaptive bounding boxes.
* **Expected Search Gain**: **~1.8× to 2.2× faster** (eliminates DRAM cache misses and pointer hops, but still requires multi-level tree traversal).

---

### Option 2: Replace the *Entire Structure* (Flat 3D Spatial Hash Grid)
You **replace the entire multi-level tree with a single-level 3D spatial hash table**:
* **How it works**:
  * Points are discretized directly into 3D voxel cells:
    $$\text{cell}_x = \lfloor X / r \rfloor, \quad \text{cell}_y = \lfloor Y / r \rfloor, \quad \text{cell}_z = \lfloor Z / r \rfloor$$
  * To search radius $r$, you query the target cell and its 26 direct 3D neighbors ($3 \times 3 \times 3 = 27$ cells total) in $O(1)$ direct array lookups.
  * Zero tree levels, zero traversal depth, zero pointers.
* **Pros**: Maximum possible speed (**5.6× faster search**, **162 ms vs 916 ms** on 55k points).
* **Cons**: Grid cell size is tuned to the expected search radius ($r = 0.15\text{--}0.25\text{m}$).

---

### Comparison Summary

| Metric / Feature | Current `PointerOctree` | Option 1: Linear Array Octree | Option 2: Flat 3D Spatial Grid |
| :--- | :---: | :---: | :---: |
